Why this doc exists

A full read-through of every controller, service, repository, and security filter in the backend, looking for logic worth documenting and bugs worth fixing before this hits production. This page is the record of that pass: what was already solid, what got fixed, and what's still genuinely missing.

What's Already Solid
🔐
Authentication & sessions
Register/login issuing JWT access tokens plus opaque, hashed refresh tokens stored server-side. Refresh rotates on every use with reuse detection — presenting an already-used refresh token now atomically revokes every session for that user instead of racing.
AuthServiceImpl · JWTService · RefreshTokenRepository
📧
OTP-based password reset
6-digit code emailed to the user, held in Redis with a configurable TTL, exchanged for a short-lived reset token on success. Comparison is now constant-time and a wrong guess no longer burns the code.
VerificationServiceImpl · OtpController · OtpGenerator
📋
Assignments, tasks & attachments
Assignments own tasks; tasks carry status, assignees, manual sort order, checklists, and Cloudinary-backed file attachments. Progress recalculates automatically from task completion on every create/delete/status change.
AssignmentServiceImpl · TaskServiceImpl · AttachmentServiceImpl
🚦
Rate limiting & role-based access
Per-IP token-bucket limiting on login, register, OTP, search, and invite endpoints, tunable via config. Role seeding and an idempotent admin seeder run automatically on startup.
RateLimitFilter · RoleSeeder · AdminSeeder
Fixed In This Pass
SeverityIssueFix
High Refresh-token rotation had a race: two concurrent requests with the same token could both pass the revoked check and both rotate successfully, defeating reuse detection. Rotation is now an atomic conditional UPDATE ... WHERE revoked = false; the loser is treated as reuse and every session for that user is revoked.
High A wrong OTP guess deleted the code from Redis anyway, forcing a full resend on a single typo. The code is now only consumed on a successful match; comparison also switched to constant-time.
High Password reset never revoked existing sessions — a stolen refresh token survived the very action meant to lock an attacker out. resetPassword now revokes all refresh tokens for the user.
Medium Login returned different status codes/messages for "no such user" vs. "wrong password," letting callers enumerate valid accounts. Both paths now return the same 401 Invalid credentials.
Medium Deleting a task could leave a gap in sortOrder; the next created task derived its position from a row count, so it could collide with a surviving task's order. Next position now derives from MAX(sortOrder) + 1 via a dedicated query.
Medium Revoked refresh tokens sat in the database until their original expiry date — the daily cleanup job only purged by expiry. Cleanup query now also removes any row with revoked = true, regardless of expiry.
Medium An attachment upload could succeed on Cloudinary and then fail to save in the database, leaving the file orphaned (and billed) forever. The DB save is now wrapped so a failure triggers cleanup of the just-uploaded Cloudinary asset.
Low Cookie names ("accessToken", "refreshToken") were duplicated as string literals across three files — one typo away from silently breaking auth. Centralized as constants on CookieUtil.
Low An empty email query param on user search matched every user as a zero-length prefix. Added @NotBlank plus a matching ConstraintViolationException handler so it fails as a clean 400.
Low Naming/cleanup: healthController → HealthController, empty vestigial AppConfig removed, dead @Component on a static-only utility class removed, redundant hand-written getters/setters removed, an unused import removed, and reset-token TTL was hardcoded where OTP TTL was already configurable. Cleaned up; reset-token TTL now reads from app.security.reset-token.validity-minutes.

Still Open
Biggest gap

Collaboration invites don't actually work end-to-end

An assignment owner can create and revoke a pending invite, but nothing anywhere ever moves an invite to ACCEPTED or DECLINED — there's no accept-by-token endpoint. Practically, AssignmentAccessGuard's member check can never see an accepted invite, so only the owner (or a global admin) can ever access a shared assignment today. Needs a real accept/decline flow, invite expiry, and linking an invite to a user who signs up after being invited.

Architecture decision, not a bug

CSRF is disabled while auth rides on cookies

The app is a stateless JSON API with CSRF turned off, but access/refresh tokens are httpOnly cookies that browsers attach automatically. The only thing standing in for CSRF protection is the CORS origin allow-list — it must never be loosened to *. Worth a deliberate decision (re-enable CSRF, or move to header-only bearer auth) rather than leaving it implicit.

Depends on infrastructure, not code

Rate limiting trusts client-forwarded IP headers

RateLimitFilter resolves the caller's IP from CF-Connecting-IP / X-Real-IP / X-Forwarded-For, all of which are client-controllable unless the reverse proxy strips them first. The limiter's entire guarantee depends on Cloudflare + nginx always sitting in front of this app — if that chain is ever bypassed, rate limiting bypasses with it.

Not built yet

Schedules, group chat, notifications, AI study plans

On the product roadmap but not present in this codebase — no entities, no dependencies, no endpoints for any of them yet.

💡
Where to look next

The invite/accept flow is the highest-value next feature — it's the one thing standing between "assignments exist" and "assignments are actually collaborative." Everything else flagged above is either a documented trade-off or a smaller, contained fix.
